- (constraint) INHERITED STACK, decided upstream in PRD 6.2 and the addendum, not open here: Turborepo with pnpm workspaces; NestJS + Prisma + PostgreSQL on the API; Next.js + React + MUI on the web; JWT auth with argon2 hashing (covers both the Parent Account password and the Parent PIN); local-filesystem storage for Page Images; Playwright for E2E; Docker Compose in development. Reused from the sibling n-electric project, including its OpenAI client configuration (@Global module, OPENAI_API_KEY, 30s timeout, maxRetries 2). Hard OpenAI dependency with no provider abstraction, accepted as a speed-over-insurance trade in PRD 9.2.
- (constraint) INHERITED PRODUCT SHAPE: one Parent Account is the only credentialed actor; Student Profiles have no credentials; Student Mode is the device default and Parent View is PIN-gated with a 15-minute silent idle timeout; Admin is a separate surface outside any Parent Account. Four AI call classes with different cost and latency profiles: Extraction (vision, up to 10 images, the most expensive), generation, grading, Explanation. Four grade states — correct, incorrect, unanswered, ungraded — carried through Attempt storage, the answer key, the parent drill-down and Mastery. Three allowance counters — Upload, Generation, Explanation — resetting on the calendar month in each Parent Account's own local timezone.
- (direction) Coaching path chosen. Spine is the only deliverable — no additional human-facing rendering requested.
- (decision) EXECUTION MODEL: expensive model calls are QUEUED JOBS, not in-request work. A request that triggers one enqueues it and returns; the job outlives the connection. The parent's progress screen reads JOB STATUS rather than holding a connection open. Binds: every caller of an expensive model path, the progress surface, and any retry or failure handling. Prevents: two units choosing incompatibly between a long-held HTTP request and a background handoff, which would give the product two different failure models and two different progress mechanisms for the same class of work. Also resolves the inherited 30-second OpenAI client timeout for Extraction, since a job is not bound by a request timeout — though the per-call timeout for a 10-image vision call still needs its own value.
- (decision) CALL-CLASS SPLIT. Queued: Extraction and generation (slow, expensive, already have a progress surface) and GRADING. Foreground, in-request: Explanation. Binds: every AI call site and the surfaces that read their results. Prevents: a unit choosing to queue an Explanation and building a progress screen for what must feel like a tap, or choosing to run Extraction in-request and inheriting the 30-second client timeout. Explanation stays foreground because the PRD requires it to stay short enough not to break a study session and the UX specified an inline loading state with manual retry on failure — a queue would give it the wrong feel and the wrong failure model. Grading queues, and this is the load-bearing insight: FR-22's 'ungraded' IS THE QUEUE-PENDING STATE. Submit enqueues grading; the results screen renders immediately with deterministic Multiple Choice grades and the AI-graded items marked 'Not graded yet'; FR-22's retry-on-next-view becomes 'read the job result if it has finished, re-enqueue if it failed'. This is not a workaround — it is the mechanism the PRD already specified, with a job behind it, and it satisfies the requirement that results appear immediately without making a student wait on a model call.
- (decision) QUEUE SUBSTRATE IS POSTGRES-BACKED, not Redis-backed. No new service: Docker Compose stays at the services already required, and there is one datastore to run, back up and reason about for a product with one operator. Binds: the job runner, every enqueue site, and the progress and status surfaces. Prevents: half the system assuming jobs are transactional with application data while the other half assumes an external broker — which changes what 'the job succeeded' can be trusted to mean. THE LOAD-BEARING PROPERTY, and the reason this is not merely an infrastructure preference: jobs live in the same database as the data they mutate, so ENQUEUEING WORK AND MUTATING STATE CAN SHARE ONE TRANSACTION. FR-31 charges an allowance on successful production rather than on request, and with a queue in a separate store 'the job succeeded but the debit did not' becomes a real and unrecoverable failure mode. Concrete library version to be bound after the web check returns. Scheduled work — per-account monthly counter resets in each account's own timezone, the FR-32 90-day Page Image expiry, and the FR-35 TTL sweep — must be served by this same mechanism or by one explicitly named companion; it is not yet decided which, and a second scheduling mechanism appearing alongside the queue is the divergence to avoid.
- (decision) MASTERY IS STORED, AND GRADING OWNS IT. Analytics reads Mastery and never computes it; no other module writes it. Binds: grading, Analytics, the parent grade override path, and anything that resolves an ungraded Question. Prevents: Analytics deriving Mastery on read while grading also persists it, which would give the product two implementations of one formula that drift the moment the rolling window or the exclusion rules change. CRITICAL CONSEQUENCE — MASTERY MUST BE RECOMPUTED FROM THE WINDOW, NEVER INCREMENTED. FR-26 defines it over a rolling window of the 5 most recent QUALIFYING Attempts per Topic, first-Attempt-only with retakes excluded, and FR-26 plus the Q8c and Q13d decisions exclude unanswered and ungraded from the denominator. A new qualifying Attempt therefore pushes an older one OUT of the window for that Topic, so the stored value is a function of a moving set rather than a running total. An incremental update — add one correct, add one to the denominator — produces a number that silently diverges from the definition and cannot be reconciled afterwards. Recompute triggers, all of which must hit the same code path: a grading job completing, an ungraded Question resolving on retry, a parent grade override under FR-25, and any new qualifying Attempt. Whether recomputation runs inside the grading transaction or as its own job is not yet decided.

- (constraint) SHARP EDGES found in the version check, each of which would bite on day one. (1) Prisma's npm 'latest' tag currently resolves to 8.0.0-rc.12 while @prisma/client latest is the stable 7.10.0 — installing prisma today ships a release-candidate CLI against a stable client by accident. Pin BOTH explicitly to 7.10.0. (2) Prisma 7 removed the bare-connection-string constructor: PrismaClient MUST be constructed with a driver adapter (@prisma/adapter-pg). This is not optional, and it happens to be exactly what pg-boss's transactional enqueue requires anyway. The generator also changes from prisma-client-js to prisma-client. (3) The inherited 30-second OpenAI client timeout is too tight for a 10-image vision call and the SDK retries the WHOLE multi-image request, so 30s x 3 attempts is 90 seconds of guaranteed failure. Needs a per-request override of 120-180s on the vision path, or background mode. (4) pnpm 12.2.1 published today while latest still says 11.25.0 — pin via packageManager and let Corepack enforce it.
- (decision) MODEL FAMILY IS GPT-5.6, replacing the gpt-4o / gpt-4.1 / gpt-4.1-mini named in the inherited n-electric config. Per call class: Extraction (vision over up to 10 photographed pages) uses gpt-5.6-sol, the flagship, because photographed handwriting plus layout extraction is the one place fidelity pays for itself and a bad Extraction poisons every Practice Test generated from it; generation uses gpt-5.6-terra; grading and Explanation use gpt-5.6-luna, grading being the volume driver. Binds: all four call sites and the cost-attribution logging in PRD 10 Observability. Prevents: call sites independently picking model tiers, which would make cost attribution meaningless and quality inconsistent across the four paths. Model IDs are PINNED AS SNAPSHOT IDS IN CONFIGURATION, never inlined in code — OpenAI is retiring models in roughly six-month waves (shutdowns confirmed for 2026-10-23 and 2026-12-11) and 4.x is late in its life, so a model name in code is a scheduled outage.
- (decision) STRUCTURED OUTPUT: the RESPONSES API with Structured Outputs and a JSON schema, using zodTextFormat from openai/helpers/zod in SDK 7.8.0. Not Chat Completions' response_format, and never the legacy response_format json_object, which guarantees only parseable JSON rather than schema conformance. Binds: Extraction, generation, and grading — every call whose output is parsed rather than displayed. Prevents: one call class validating against a schema while another trusts a JSON blob, which is how an Extraction silently produces a Question the rest of the system cannot read. OpenAI's own migration guidance recommends Responses for all new projects; the Assistants API was sunset 2026-08-26.
- (decision) MASTERY RECOMPUTE RUNS INSIDE THE TRANSACTION OF WHATEVER CHANGED A GRADE — the grading job, the ungraded-retry resolution, and the FR-25 parent override all recompute before they commit. Binds: grading, the retry path, the override path, and Analytics reads. Prevents: a window in which a grade exists and Mastery does not yet reflect it, which the parent dashboard can read — producing a number that is wrong rather than merely stale, on the surface whose entire purpose is a truthful Weak Area call. Chosen over a separate recompute job because at v0 volumes the recompute is a handful of rows per Topic, and the Postgres-backed queue makes grade-and-Mastery-land-together free rather than a distributed-transaction problem. Revisit if recompute cost ever approaches the grading call itself.
- (decision) TOPIC NORMALIZATION IS A THREE-STAGE CASCADE BEHIND ONE INTERFACE — normalize(label, subjectId) returns a canonical Topic id. This closes what PRD 12.2 item 2 calls the highest-risk requirement in the build. Stage 1: normalize and exact-match (lowercase, strip stopwords, sort tokens), which catches 'remainder division' against 'division with remainders' at zero cost and zero latency. Stage 2: embed the emitted label once with text-embedding-3-small and cosine-compare IN APPLICATION CODE against the cached canonical vectors for that Subject, threshold approximately 0.85 — tens of dot products over 1536 floats, microseconds, with the vectors stored in an ordinary Prisma column. Stage 3: one gpt-5.6-luna call with the candidate list in the prompt when cosine falls below threshold; this is also the only stage that can conclude NONE OF THESE FIT, which is where a genuinely new canonical Topic comes from. Binds: generation (which emits the labels), Mastery (whose per-Topic numbers depend on the merge being right), and Analytics. Prevents: two call sites matching Topics by different rules, which splits one concept into two Mastery values and makes every Weak Area call noise. PGVECTOR EXPLICITLY REJECTED at this scale: Prisma 7.10.0 still has no native vector type, so the column would be Unsupported(vector(1536)) with the generated client permanently unusable for it and raw SQL forever; prisma migrate emits neither CREATE EXTENSION nor the index; the community extension has been unmaintained since 2024-07-04; and pgvector's own documentation says a table scan may beat an index on a small table. The canonical set is tens of entries per Subject. The single interface is what makes this reversible — any stage can be replaced without touching a caller.
- (decision) A STAGE-3 TOPIC PROPOSAL IS TAGGED PROVISIONALLY AND QUEUED FOR THE OPERATOR. The Question receives the proposed Topic immediately so Mastery keeps accruing, and the Topic carries a provisional flag until an operator confirms it, merges it into an existing canonical Topic, or renames it. Binds: normalization, the Admin surface, Mastery, and Analytics. Prevents: the canonical set growing unsupervised — the bloat PRD 14 flagged when it deferred the curation tool — where a near-duplicate that slips through splits one concept into two Mastery values with no signal that it happened. Rejected: self-adding, which has no correction path and whose failure is invisible; and queue-without-tagging, which protects the taxonomy by putting a hole in the only signal a Free-tier parent receives, on an account with two Practice Tests a month. ACCEPTED COST THAT MUST BE BUILT FROM THE START, NOT RETROFITTED: a merge re-points every Question already tagged with the merged Topic and recomputes the Mastery of every affected Student Profile. That is real work, it runs through the same recompute path as every other Mastery trigger, and building it later means shipping a curation tool that silently corrupts historical Mastery. This also gives the deferred PRD 14 curation tool its shape: confirm, merge, rename, backed by a provisional-Topic queue.
- (decision) MODE IS CARRIED IN THE JWT, WITH SLIDING EXPIRY. The token identifies the Parent Account and carries the mode; crossing the Parent PIN mints a token with Parent View scope, and every parent-scoped endpoint requires that scope server-side. Binds: every API route, the Next.js app, and the FR-35 restore path. Prevents: Student Mode being enforced by client routing on one surface and by a server check on another — which is the failure PRD 10 names explicitly when it says Student Mode restrictions are not client-side-only, and which FR-4 forbids when it bars reaching an upload or generation surface by direct URL. SLIDING EXPIRY: every parent-scoped request returns a refreshed token carrying a new 15-minute window, so genuinely active work never expires while 15 minutes of real inactivity does. An absolute expiry was rejected because it would interrupt a parent mid-review at the 15-minute mark regardless of activity, and since FR-34 deliberately fires without warning, that work would vanish with no chance to prevent it — FR-35 would be compensating for a self-inflicted wound rather than for a genuine interruption. Refresh-token pairs were rejected as moving the idle problem onto the refresh token rather than solving it. TWO BINDING RULES: the parent-scoped token is held IN MEMORY ONLY and never persisted to disk or local storage — the threat model is a curious child on a shared family tablet, and a persisted token survives the app being closed and reopened, which is precisely the forgotten-session case the timeout exists to close. And the FR-35 restore of uncommitted parent state is gated on presenting a parent-scoped token, which is what makes 'restored strictly after PIN re-entry' a server-side guarantee rather than a client-side promise.
- (decision) ALLOWANCES ARE DERIVED, NOT DECREMENTED. There is no counter column and no reset job. Usage for a period is a COUNT over the artifacts themselves, scoped to the Parent Account and to the period window computed from the account's stored IANA timezone: Upload Allowance = Source Tests created in window; Generation Allowance = Practice Tests whose status has ever reached draft; Explanation Allowance = Explanation rows generated in window on Free tier. Binds: every path that gates on allowance (upload, generation enqueue, foreground Explanation) and every path that produces a chargeable artifact. Prevents: four independent counting implementations drifting apart; a debit forgotten or double-applied; two concurrent requests each passing a stale remaining-count clamp; a per-account midnight reset job that breaks on DST. FOUR BINDING RULES. (1) The cap check and the artifact INSERT occur in the SAME transaction — the count is taken inside the transaction, so serialization at the DB is what enforces the cap, not an application-level clamp. (2) Chargeable artifacts are NEVER hard-deleted; consumption is a fact about history, so retirement is a status change and the row remains countable. This makes FR-32/FR-33 deletion an explicit interaction to resolve: deletion must not refund. (3) A Practice Test charges on first reaching draft and never again — the countable predicate is 'has ever reached draft', which requires a durable marker on the row rather than reading current status. A queued generation job producing 1-5 drafts therefore charges exactly per draft that lands, and a job that fails after three drafts has charged three. (4) FR-39 interaction: a SUPPRESSED Explanation still counts as consumed, and the free regeneration it entitles must NOT count again — carried as a flag on the regenerated row excluding it from the count, not as a second counter. Rejected: an authoritative AllowanceLedger decremented per artifact, because it requires row locking to be race-safe, a reconciliation job to be trustworthy, and a per-account timezone-scoped reset scheduler; at tens of artifacts per account per month the count query is an index scan and buys none of that complexity.
- (decision) STORED BYTES ARE NEVER THE AUTHORITY; A ROW IS, FROM THE FIRST BYTE. No code path writes a file that has no owning database row, and no code path enumerates the filesystem to find work. Binds: capture and upload (FR-5), Source Test commit, Extraction, FR-32 retention, FR-33 deletion, FR-35 uncommitted parent state, and any future stored artifact. Prevents: bytes on disk reachable by no rule; a directory scan and a table query disagreeing about what exists; deletion that misses files because it enumerates by Student Profile while the files were never attached to one. FIVE BINDING RULES. (1) A PageImage row is INSERTed in state 'uploading' BEFORE any byte is written, and the storage path is DERIVED from the row's identifier - never supplied, influenced, or named by the client. This is also the path-traversal control: there is no client-controlled component in a filesystem path. (2) Every stored artifact therefore has an owner, a created timestamp, and a state, which collapses orphan cleanup, retention, and deletion into ONE mechanism: a sweeper over ROWS, never a scan over DIRECTORIES. An abandoned capture is not a special case - it is a row stuck in 'uploading' past its TTL. (3) FR-35 uncommitted parent state is stored under the same treatment: a row, owned by the Parent Account, with a state and a TTL, swept by the same mechanism, and readable only on presentation of a parent-scoped token per the mode-gate decision. (4) DELETION IS A STATE TRANSITION, NOT A ROW REMOVAL. FR-32 and FR-33 unlink the file and blank the content-bearing columns; the row survives in a 'deleted' state retaining only its identifiers, timestamps, and account scope. This is what reconciles deletion with derived allowances - the husk stays countable, so deleting a Student Profile CANNOT refund Generation or Upload Allowance, and delete-and-retry is not a path to unbounded Free-tier usage. (5) An abandoned capture consumes NOTHING. FR-31 charges on successful production, and an Upload Allowance is charged against the Source Test, not against the pages; a capture that never commits produces no Source Test and so is not counted. The swept 'uploading' row is deleted outright rather than husked, because it never charged anything there is nothing to keep it countable for.
- (decision) ONE UNCOMMITTED-STATE LIFECYCLE WITH A SINGLE 72-HOUR TTL. FR-35 restorable parent state and the orphaned-capture sweep are the SAME mechanism viewed at two moments, not two mechanisms: a row holding uncommitted work is restorable FR-35 state until its TTL elapses and an orphan after it, so SWEEPING IS EXPIRING FR-35 STATE. This resolves the direct contradiction between the two rules, which otherwise point opposite directions at the same PageImage row in 'uploading' - one promising restoration, the other reclaiming it. Binds: FR-5 multi-page capture, FR-35 restore, the orphan sweeper, and any future uncommitted-work surface. Prevents: a sweeper deleting the exact pages FR-35 promised to give back; two clocks drifting apart; a second retention concept accreting for non-image parent state. FOUR BINDING RULES. (1) ONE TTL, 72 hours from row creation, applied uniformly to uncommitted state whether or not it carries bytes - captured pages and non-image parent state are not treated separately. 72h is chosen to survive an ordinary interrupted weekend, because re-photographing a physical test is the most expensive action this product ever asks of a user and a stingy TTL is experienced as data loss. (2) The TTL is a FLOOR ON RETENTION, NOT A CEILING ON PROTECTION: within the window the state remains gated on a parent-scoped token per the mode-gate decision, so a child on a shared family tablet cannot restore it either. (3) TTL is measured from row creation and is NOT extended by activity - an uncommitted capture does not become permanent by being touched. (4) Expiry deletes the row outright rather than husking it, per the abandoned-capture rule: nothing was charged, so nothing needs to stay countable.
- (decision) MODULE BOUNDARIES: ONE WRITER PER ENTITY, AND THE MODULE THAT WRITES AN ENTITY OWNS IT. Every other module reads through that module's service and NEVER through Prisma directly - no module touches another module's Prisma delegate, for read or write. Binds: every module, every query, every migration that adds an entity. Prevents: two modules computing the same derived value differently (the analytics surface recomputing Mastery its own way is the concrete case); 'who can change this row' becoming unanswerable; a schema change rippling into modules that had no business knowing the shape. Generalizes the already-settled 'grading owns Mastery' call into the project-wide rule. DECOMPOSITION BY OWNED ENTITY CLUSTER: identity owns Parent Account, Student Profile, sessions. sourcetest owns Source Test and Page Image. extraction owns extracted Question content on the Source Test. practicetest owns Practice Test, Question, Attempt, Answer. grading owns grade state and Mastery. explanation owns Explanation, suppression state, and flags. topics owns Topic, the canonical set, and the provisional queue. allowance OWNS NO ENTITY - it is a POLICY module, not a data module, holding the period-window computation and the countable predicates and reading counts across sourcetest, practicetest, and explanation. That it owns nothing is a direct consequence of the derived-allowance decision and is deliberate. AI CALLS ARE CENTRALIZED IN ONE ai MODULE, WITH PROMPTS EXCLUDED. The ai module owns the OpenAI client, the pinned model snapshots, the Responses API and zodTextFormat structured-output plumbing, retry and timeout policy, and token/cost accounting; domain modules call it with a typed request. CARVE-OUT: PROMPT TEXT STAYS IN THE DOMAIN MODULE that needs it, because a prompt is domain knowledge and centralizing prompts would create a module that must understand every domain in order to be edited. Prevents: four independent retry policies producing an unbounded spend bug; PRD section 10 per-account cost attribution having no single place to be implemented; a model swap requiring four coordinated edits. Rejected: each domain module holding its own OpenAI client, on those same three grounds.
- (decision) SPLIT CREDENTIALS: A PERSISTENT SESSION COOKIE FOR IDENTITY, AN IN-MEMORY ELEVATION TOKEN FOR PARENT VIEW. Two credentials with different lifetimes and different storage. (1) The SESSION credential is an httpOnly, Secure, SameSite=Strict cookie the browser JavaScript cannot read. It answers WHICH ACCOUNT and survives refresh, so Next.js can server-render the shell and anything student-scoped without a loading flash. (2) The ELEVATION credential is the parent-scoped token from the mode-gate decision: held in a React context in memory ONLY, never written to cookie, localStorage, sessionStorage, or disk, and lost on any full page load. It answers ELEVATED TO PARENT VIEW. Binds: every endpoint, every page, the Next.js rendering strategy, and the FR-35 restore path. THREE BINDING RULES. (a) NO PARENT-SCOPED DATA IS EVER SERVER-RENDERED. Parent surfaces fetch client-side carrying the elevation token; a parent screen that renders on the server is a bug, because the server would have had to obtain the elevation from something persistent. This makes the mode gate STRUCTURAL rather than a UI convention - parent data physically cannot appear without an elevation the browser never stored. (b) A refresh or hard navigation drops the parent to the PIN. This is intended behavior on a shared family tablet, not a defect, and it is why FR-35 exists; the two decisions interlock, with FR-35's 72-hour uncommitted-state window catching the work that a dropped elevation would otherwise lose. (c) The session cookie alone NEVER satisfies a parent-scoped endpoint; server-side scope checks require the elevation token, so possession of the cookie by a curious child grants student scope only. Rejected: carrying the parent token in an httpOnly cookie for SSR convenience - the child does not need to READ the token, only to make the browser SEND it, so a cookie survives refresh and converts 'PIN re-entry' into 'PIN once per login', defeating the feature entirely. Also rejected: an all-client-rendered app with the session in memory too, which is honest to the threat model but pays a loading state on every student screen for no security gain, since student scope is not what the PIN protects. Accepted cost: two auth paths to keep straight.
- (decision) OPERATIONAL ENVELOPE: RATIFY THE n-electric DEPLOY PATTERN ON A DIGITALOCEAN DROPLET, DRIVEN BY GITHUB ACTIONS. Reference implementation is /Users/rvnadela/projects/n-software/n-electric (scripts/deploy.sh, compose.production.yml, infra/docker/Caddyfile, infra/terraform/). Binds: deployment, environments, TLS, migrations, and the storage assumptions every earlier decision rests on. THE SHAPE. Single hand-provisioned Droplet running Docker Compose; images built in CI for linux/amd64 and pushed to GHCR tagged with the commit SHA and latest; the compose file and Caddyfile are scp'd from the repo on every deploy, so the REPO IS THE SOURCE OF TRUTH AND HOST COPIES ARE DISPOSABLE; the release pointer is the image tag lines in the host's /opt/.../.env, rewritten in place, after which compose reconciles; Caddy terminates TLS with automatic ACME and persists certs in a caddy_data volume; state lives in named Docker volumes (postgres_data, caddy_data, uploads_data). ONE ENVIRONMENT, PRODUCTION ONLY - no staging tier in v0. MIGRATIONS ARE A DISCRETE ONE-SHOT STEP (docker compose run --rm) THAT RUNS BEFORE compose up, NEVER ON CONTAINER BOOT - critical here because api and worker are the same image with different entrypoints and would otherwise race the same migration lock on start. DELTAS FROM THE REFERENCE, all deliberate. (1) CI/CD IS ON. n-electric renamed both workflows to .yml.disabled to save Action minutes and deploys from the developer laptop via 'pnpm ship'; here deploy.yml is live, triggered on push to main, using the environment 'production' and the secrets DROPLET_IP, SSH_PRIVATE_KEY, GHCR_TOKEN. Building in CI also removes the cross-architecture --platform linux/amd64 workaround. (2) BACKUPS COVER UPLOADS, NOT JUST POSTGRES. The cloud-init cron is extended to snapshot the uploads volume alongside pg_dump, written together with the same 7-day local retention, because restoring the database alone yields rows pointing at files that no longer exist - the precise failure the row-is-authority rule exists to prevent. Page Images are the only artifact in this product that CANNOT be regenerated; recovery means asking a parent to re-photograph a physical test they may no longer possess. (3) ROLLBACK TARGETS THE PREVIOUS SHA TAG, never :latest. The reference workflow rolls back by pointing .env at :latest, but the same run has already pushed :latest to the new build, so its rollback restores the thing that just failed. (4) DROPLET SIZED 4GB MINIMUM, not the reference's s-1vcpu-2gb, because this stack adds a worker container to api/web/postgres/caddy and the AI call path holds image payloads in memory. NOT COPIED FROM THE REFERENCE: committed terraform.tfstate and terraform.tfvars; the droplet IP hardcoded in the repo; and Dozzle exposed publicly behind basic-auth with /var/run/docker.sock mounted, which is a container-escape path unacceptable on a host holding children's data.
- (question) DEFERRED: OFFSITE BACKUP OF UPLOADED PAGE IMAGES. v0 backs up the uploads volume to LOCAL DROPLET DISK ONLY, on the same cron and 7-day retention as pg_dump. This survives a bad deploy, a bad migration, or an accidental volume removal, but NOT loss of the droplet itself - if the host is destroyed, every family's photographed Source Tests are gone permanently and are unrecoverable by any means, because the physical tests they were photographed from are typically no longer in the parent's possession. ACCEPTED RISK FOR v0, EXPLICITLY. Planned resolution: push the local snapshot offsite to CLOUDFLARE (R2) after it is written - a single rclone/s3cmd step appended to the existing backup script, requiring a bucket and one credential on the host, with no change to any other decision. Deliberately chosen over DigitalOcean Spaces. REVISIT CONDITION: before the first real family's data lands, or at the first paying account, whichever comes first - the risk is acceptable while the only data at stake is the team's own test uploads and stops being acceptable the moment it is someone else's irreplaceable material.
- (decision) COST ATTRIBUTION IS A TABLE, NOT A LOG STREAM. The ai module writes an AiCall row per completed provider call: Parent Account, call class (Extraction, Generation, Explanation, Topic normalization), pinned model snapshot, input and output token counts, computed cost, latency, and the correlation identifier of the request or job that caused it. Owned by the ai module per the one-writer rule; nothing else writes it. Binds: PRD section 10 per-account cost attribution, every AI call path, and any future spend ceiling. Prevents: 'which accounts cost the most this month' being unanswerable; cost history destroyed by log rotation; a spend cap with nothing to enforce against. RATIONALE. Section 10 is a PRODUCT requirement, not an ops nicety - it must be queryable by account and by period, which is a SQL question against a database that already exists. It is the same discipline as the derived-allowance decision: the answer is computed from durable rows, not caught from a stream in flight, so allowances count artifacts and cost sums calls with one shared habit rather than two mechanisms. It is also the only possible enforcement point for a spend ceiling, because a log line cannot be transacted against. The write is effectively free at this scale and lands with the call that produced it. Rejected: emitting a structured log line per call, which needs a log aggregator this single-droplet deployment does not have and cannot retain history through rotation. TWO ACCOMPANYING RULES, both binding on all modules. (1) CORRELATION IDENTIFIER: one is minted at HTTP request entry or job start and threaded through every log line and every AiCall row. Without it a failed queued generation is unfindable, because the error is in the worker's output and the request that caused it is in the api's, on the same host with no common key. (2) NO LOG LINE, TRACE, ERROR REPORT, OR AiCall ROW EVER CARRIES Page Image bytes, extracted Question content, Explanation text, or a child's Answers. Identifiers only. This is not a privacy preference but a hard boundary given the subject population. Logging shape: structured JSON to stdout, with Docker log driver rotation limits declared in the compose file - the n-electric reference omits them, which is a slow disk leak on a small droplet.
- (decision) EXTERNAL ERROR TRACKING VIA SENTRY (FREE TIER), WITH DEFAULT CAPTURE AGGRESSIVELY DISABLED. api, web, and worker all report unhandled exceptions to one Sentry project, tagged with the release SHA already carried by the deployed image tag. Binds: all three runtime containers and the logging boundary rule. RATIONALE: the alternative of stdout-only leaves NO FAILURE NOTIFICATION WHATSOEVER, and a queued job dying silently in the worker is the most likely failure mode in this design - nobody is reading the worker's stdout at 9pm, and the parent finds out before the operator does. Grouping, alerting, and release attribution are what is being bought; convenience is not the argument. MANDATORY CONFIGURATION, not optional hardening: sendDefaultPii false; request body capture off; local variable capture off; cookie and header capture off; and an explicit beforeSend denylist. This is load-bearing because Sentry's DEFAULTS capture request bodies and local variables, which is precisely where extracted Question content, Explanation text, or a child's Answers would leak - the no-content logging rule stops being something the code merely follows and becomes something that must be actively CONFIGURED against a third party that would otherwise collect it. Sentry is therefore an accepted additional data processor touching the application, justified only under that configuration. Deployment note: the release tag is the commit SHA already used for the GHCR image and the rollback pointer, so error grouping, the deployed artifact, and the rollback target all name the same thing.
- (decision) TESTING: THE ai MODULE BOUNDARY IS THE ONLY TEST SEAM FOR NONDETERMINISM. Every test double swaps that one interface - the same module that owns transport, model pinning, structured-output plumbing, and accounting. Domain modules never know whether the provider was real, and no domain module may be written in a way that requires knowing. Binds: all test tiers, CI, and the ai module's public interface. Prevents: four nondeterministic, slow, paid call paths leaking into the everyday test loop; per-domain mocking strategies drifting apart. THREE TIERS. (1) Unit and integration: ai faked, returning canned structured payloads, against a REAL POSTGRES IN A CONTAINER - an in-memory or faked database would invalidate nearly every decision in this spine, because the allowance cap check, the derived counts, the transactional enqueue, and the deletion husk are all DATABASE behaviors, not application logic. Deterministic and fast. (2) End-to-end with Playwright: full stack, ai still faked. Owns the flows, the Student/Parent mode gate, and the queue-and-poll progress screen. Its purpose is NOT to judge answer quality but to detect that a pinned model snapshot has been retired or that a structured-output schema no longer validates against the live provider. THE SCHEMA IS THE CONTRACT: because every AI call goes through Responses API Structured Outputs with a Zod schema, a fake returning a schema-valid payload is a FAITHFUL stand-in for everything downstream, since downstream code cannot legally depend on anything the schema does not guarantee. This is a consequence of the structured-output decision that was not among its original reasons. BINDING RULE ON THE FAKE: it MUST be able to fail, not only succeed - timeouts, provider refusals, schema-invalid responses, and partial success on a multi-draft generation job. Those failure paths are load-bearing in this design (per-draft allowance charging on partial failure, ungraded as the queue-pending state, retry-on-next-view), and a fake that only ever succeeds leaves every one of them untested while appearing to have coverage.
- (decision) ABUSE DEFENSE: ALLOWANCES ARE A PRODUCT BOUNDARY, NOT A SPEND DEFENSE - A GLOBAL DAILY CEILING IS THE ACTUAL BACKSTOP. Allowances cap AI usage PER ACCOUNT, but account creation is free, so the cap is per-account and not per-person: a script that registers accounts obtains unlimited Free-tier Extraction, Generation, and Explanation calls, every one a paid provider call against the project's own API key. Binds: all unauthenticated endpoints and every AI call path. THREE RULES. (1) IP-BASED RATE LIMITS ON UNAUTHENTICATED ENDPOINTS via @nestjs/throttler - tight on signup, looser on login. In-process storage is honest here because the deployment is single-host by construction; if that ever stops being true this must move to shared storage. Login needs this independently of abuse economics: argon2 is DELIBERATELY EXPENSIVE, so a login flood is a CPU denial-of-service against a 4GB droplet, not merely a credential-stuffing risk. (2) A GLOBAL DAILY SPEND CEILING enforced against the AiCall table - TOTAL across all accounts, not per account. When the day's summed cost crosses a configured limit, new AI work is refused and an alert fires. This is the only rule in the design that FAILS SAFE against the unforeseen, including a bug of the project's own making such as a retry loop or a runaway job, and it is nearly free to implement now that cost attribution is a queryable table rather than a log stream. (3) Connection-level limits sit at Caddy, which already fronts everything. DELIBERATELY NOT IN v0: email verification gating, because it adds friction to the one flow that most needs none; CAPTCHA; and per-IP account-creation quotas beyond the simple throttle.

- (override) DELETION ERASES; AN ANONYMOUS USAGE TOMBSTONE PRESERVES THE COUNT. This REPLACES the earlier 'chargeable artifacts are never hard-deleted, deletion is a state transition leaving a countable husk' rule, which was incoherent for account erasure: a husk retaining identifiers and timestamps is genuinely hard to call erased, and FR-33 plus PRD section 5.2's child-data commitment do not permit it. (2) STUDENT PROFILE deletion: the account survives, so deleting a profile drops the derived count and returns capacity, making delete-and-recreate a path to unlimited Free tier - and not an adversarial one, since a parent deleting a profile made by mistake triggers it accidentally. RULE: on deletion the countable facts COLLAPSE INTO A USAGE TOMBSTONE keyed ONLY by Parent Account, period, call class, and count. Everything else is HARD-DELETED - Page Image files unlinked and rows removed, extracted Question content, Answers, grading rationales, Explanations, Mastery, and the Student Profile itself. - (override) IDLE TIMEOUT MEASURES INACTIVITY, CLIENT-CLOCKED, SERVER-CAPPED. This CORRECTS the earlier mode-gate rule that slid the 15-minute window on every parent-scoped REQUEST, which failed in both directions against FR-34 and EXPERIENCE.md: the AD-3 generation-progress screen polls, so Parent View would never time out on the abandoned shared tablet the rule exists for, while a parent READING a long Explanation makes no requests at all and would be dropped mid-work. The governing subtlety: READING IS ACTIVITY BUT PRODUCES NO REQUESTS, so no purely server-side rule can observe it. RULES. (1) THE CLIENT OWNS THE IDLE CLOCK, tracking real interaction - pointer, key, scroll, touch - and requesting a refreshed elevation token while the parent is active. Polling does not touch the clock, because polling is not interaction. (2) The client can only REQUEST a refresh, never extend a token: the elevation token still expires on its own 15-minute window and the server mints any replacement. (3) AN ABSOLUTE CEILING OF 8 HOURS caps total elevation regardless of activity, so an interaction loop cannot hold Parent View open indefinitely; 8h is long enough never to interrupt a real sitting and short enough that a tablet left on overnight is locked by morning. Rejected: server-side classification of endpoints as interactive versus background, which still drops the reading parent - precisely the case FR-34's wording protects - and makes every newly added endpoint a security decision that can be got wrong by omission. The standard 'do not trust the client' objection does not apply here: the threat model is an UNATTENDED tablet, not an attacker, and a child deliberately wiggling the screen to hold the session open is by definition present and interacting, which no inactivity timeout was ever going to prevent.
- (decision) GENERATION IS INCREMENTAL, AND PARTIAL SUCCESS IS A REAL USER-VISIBLE OUTCOME. Confirms the per-landed-draft charging rule and resolves its apparent conflict with EXPERIENCE.md's 'a failed generation costs nothing': that sentence is TRUE AND RETAINED, scoped to the case where ZERO drafts land. The gap was never the charging rule, it was that partial success had no existence in the UX. RULES. (1) A generation job that produces 3 of 5 requested Practice Tests reports as PARTIALLY COMPLETE: the parent receives 3 Practice Tests and is charged 3 Generation Allowance units. (2) Drafts that landed are never discarded on subsequent failure of the same job - each draft is committed as it lands, per the per-artifact charging rule. (3) A job in which nothing landed charges nothing and reports as failed. Rejected: all-or-nothing generation, which discards completed drafts and charges nothing on partial failure. It is the more elegant sentence and the worse product - the provider was already paid for those drafts either way, so rollback converts a partial success into pure loss, and a parent who watched three tests appear would see them vanish. - (decision) IN-PROGRESS ATTEMPT STATE IS CLIENT-OWNED, AND IT IS THE ONE UNCOMMITTED-STATE MECHANISM THAT IS NOT PARENT-GATED. (1) Answers within an open Attempt are held in CLIENT-SIDE PERSISTENT STORAGE keyed to the Attempt, surviving refresh and backgrounding without a network round trip. This is the only place in the design where student work lives outside the database, and it is deliberate: FR-36 requires answering and navigating to work OFFLINE inside an already-started Attempt. (2) SUBMISSION REQUIRES THE NETWORK AND IS NEVER RETRIED SILENTLY - per FR-36 the student is told, the Attempt stays open with every answer intact, and they submit again themselves. (3) TIMER AUTHORITY IS THE SERVER, EVALUATED AT SUBMIT. The Attempt carries a server-issued started-at and duration; the client renders a countdown but never decides expiry. - (decision) THE ACCOUNT TIMEZONE IS EFFECTIVE-DATED; CHANGING IT NEVER RE-SLICES A RUNNING PERIOD. Corrects the derived-allowance rule, which computed period windows from the CURRENTLY STORED zone and therefore reproduced exactly the three failures EXPERIENCE.md forbids: counts moving, a period shortened, and a reset date retroactively wrong. RULE: the Parent Account holds a timezone HISTORY of effective-dated entries rather than a single mutable field; the window for any period is computed from the zone in effect AT THAT PERIOD'S START, and a change takes effect from the NEXT period boundary. Structured Outputs guarantees a payload PARSES; it guarantees nothing about whether the content is sane. RULES. (1) Every Extraction schema field carries a self-assessed confidence of low, medium, or high, and prompts instruct the model to return null for any field it cannot read with confidence rather than guess - the mechanism behind FR-9's uninterpretable-not-hallucinated rule. Aggregate low confidence across a page is the signal behind FR-8's legibility check and FR-9a's thin-Extraction warning; those FRs had no mechanism at all before this. (2) DETERMINISTIC POST-HOC VALIDATION runs in code on every AI payload after schema validation, downgrading confidence or rejecting outright. - (decision) AI FAILURES SPLIT INTO CLIENT-FAULT AND UPSTREAM-FAULT, AND THEY DEGRADE DIFFERENTLY. Without this the queued-job retry policy re-enqueues an unusable photograph forever, burning provider spend on input that can never succeed. RULE: an unreadable or unusable INPUT is a client fault (BadRequest class) - terminal, never retried, surfaced to the parent as a retake prompt per FR-10. A provider timeout, rate limit, refusal, or outage is an UPSTREAM fault (BadGateway class) - retried with backoff, and on exhaustion surfaced as a transient failure the user can retry themselves. Grading exhaustion writes the ungraded state per FR-22; generation exhaustion leaves the job failed with whatever drafts landed already committed and charged. - (decision) TRANSACTION BOUNDARIES HAVE AN OWNER: THE INITIATING MODULE OPENS, CALLEES NEVER DO. Three ADs demand cross-module transactions while the one-writer rule forbids touching another module's Prisma delegate, leaving two equally-compliant implementations - the initiator opening a transaction and passing it down, or the callee opening its own and calling back - one of which silently loses atomicity. RULES. (1) The module that INITIATES a unit of work opens the transaction. (2) EVERY cross-module write method takes a transaction client as its FIRST PARAMETER and may never open its own transaction; a write method without that parameter is a defect. (3) A module still owns its writes - the caller supplies the transaction, never the SQL. This is what makes 'reads through the owner's service' and 'atomic across modules' hold simultaneously.
- (decision) ALLOWANCE IS A PURE PREDICATE PROVIDER, AND THE CAP IS ENFORCED BY THE DATABASE. Corrects a hole where the cap check had to run inside the owning module's INSERT transaction while the dependency graph forbids reversing the allowance arrow, forcing either a cycle or allowance writing entities it does not own. RULES. (1) allowance returns the PERIOD WINDOW and the COUNTABLE PREDICATE; the module that owns the entity executes the count inside its own insert transaction. No arrow reverses and no cycle appears. (2) THE SERIALIZATION MECHANISM IS NAMED, not asserted: the cap check runs under a transaction-scoped ADVISORY LOCK keyed on Parent Account plus call class, so two concurrent requests serialize on the same key rather than both reading a stale count. Merely being in a transaction does NOT prevent the race at READ COMMITTED, which is the default and was the unstated gap. (3) allowance therefore owns the UsageTombstone entity and is no longer an owns-nothing module.

(2) The countable predicate for Generation Allowance is 'has ever reached draft' - a durable marker on the row - so a reserved row that never becomes a draft is NOT counted. (3) On job completion, reservations that were not fulfilled are DELETED; drafts that landed stay, charged. A job producing 3 of 5 leaves 3 charged drafts and deletes 2 reservations. Closes the most-reported hole in the gate, found independently by three lenses: the session credential carried the Parent Account and the mode but NOT which child, so student-scoped endpoints could only verify account ownership and a sibling's data was reachable by editing a URL. This violates FR-4 and PRD section 10's requirement that scoping is not client-side-only. RULES. (1) Entering Student Mode for a profile MINTS A NEW SESSION TOKEN carrying that Student Profile; a student-scoped endpoint reads the profile FROM THE TOKEN and never from a request parameter. A studentProfileId in a query string or body is ignored where it appears and is a defect where it is relied upon. (2) Switching profiles requires re-crossing the mode gate - it is a new token, not a client-side selection. (3) The same rule generalizes what was previously stated for FR-35 alone: every profile-scoped read and write derives its profile from the credential.
- (decision) DESTRUCTIVE ACTIONS REQUIRE THE ACCOUNT PASSWORD, NOT THE PARENT PIN. FR-33 states this explicitly and no AD carried it, so a PIN-derived elevation token satisfied a parent-scoped endpoint and a child who watched the PIN entered on the family tablet could irreversibly erase a sibling's record. RULE: Student Profile deletion, Parent Account deletion, and early Page Image deletion require a FRESH PASSWORD RE-AUTHENTICATION in the request, verified server-side against the argon2 hash. The elevation token is necessary but NOT SUFFICIENT for these endpoints. The PIN gates a MODE; the password gates DESTRUCTION - the distinction is FR-33's, and it must be enforced at the endpoint, not in the UI.
- (decision) SUPPRESSION IS CHECKED AT SERVE TIME, NOT ENCODED IN A CACHE KEY. The previous rule - that the Explanation cache key includes the Student Profile - PARTITIONS the cache per child but does not suppress: the suppressed entry is precisely the one that key hits. This broke FR-39, and with it PRD section 5.1's entire argument for serving children unreviewed AI content, which rests on suppression being a real remedy rather than a stated one. RULES. (1) EVERY student-facing Explanation read passes a serve-time suppression check against the FR-39 suppression record for that Student Profile. There is no read path that bypasses it. (2) The Explanation cache is IN-DATABASE, not an external or in-process cache, so the suppression check and the cache read are one query and cannot diverge. (3) The cache key still includes the Student Profile - a free regeneration after suppression is a distinct entry, never an overwrite - but the key is an optimization and the serve-time check is the CONTROL. (4) A suppressed Explanation remains readable to the parent and to the admin flagged queue per FR-30a; suppression is scoped to the child's screen.
- (decision) CLIENT-HELD ATTEMPT ANSWERS ARE BOUND, EXPIRED, AND ERASABLE. As first written, client-side Attempt state recreated on the student side exactly the hazard FR-35 was written to prevent on the parent side: no TTL, no clear on profile change, and unreachable by FR-33 deletion - so one child's answers persisted in the shared origin's storage after a sibling rebound the device. RULES. (1) Client-held answers are keyed to the Attempt AND the Student Profile, and are CLEARED on any profile switch, sign-out, or mode-gate crossing. A device rebound to a sibling starts with nothing. (2) They carry the same 72-hour TTL as server-side uncommitted state, enforced client-side on read, so a stale Attempt cannot be resumed indefinitely from a device nobody has opened. (3) FR-33 deletion CANNOT reach another device's local storage, and the spine must say so rather than imply otherwise: the mitigation is the binding and the TTL, plus clearing on the next launch when the server reports the profile gone. This is a stated limitation, not a solved problem.
- (decision) JOB PAYLOADS CARRY IDENTIFIERS ONLY, NEVER CONTENT. The queue's own tables were an unenumerated store of children's data: a Generation job payload is the child's transcribed paper, pg-boss archives completed jobs, and no rule, owner, retention pin, or deletion path covered them. RULES. (1) Every job payload contains IDENTIFIERS AND PARAMETERS ONLY; the handler loads content from the database at execution time. No extracted Question content, Answer, Explanation text, or image bytes ever enters a job payload. This makes the queue tables non-sensitive by construction rather than by a deletion sweep that would have to chase them. (2) pg-boss archive and retention windows are configured explicitly rather than left at defaults. (3) The same rule extends the existing logging boundary: identifiers only, in logs, error reports, AiCall rows, and now job payloads.
- (decision) DELETION ENUMERATION IS EXHAUSTIVE AND WRITTEN DOWN. Four stores survived FR-33 with no path visiting them. RULES. (1) AiCall rows are ANONYMIZED on Student Profile deletion and DELETED on Parent Account deletion, keeping the cost history the spend ceiling needs while removing the link to a person; the surviving aggregate is the same class of fact as a usage tombstone. (2) AdminAudit rows retain the ADMIN ACTION and the account identifier but never child content, and survive deletion deliberately - an audit trail a deletion can erase is not an audit trail. This must be stated, not implied. (3) Job payloads are already identifier-only, so no deletion path is needed for them; queued jobs referencing deleted rows fail closed and are discarded. (4) Client-held Attempt state is out of reach and is documented as a stated limitation. (5) The enumeration itself is a maintained list: adding a store without adding it to the deletion enumeration is a defect.
- (decision) SENTRY SCRUBBING IS MESSAGE-LEVEL, NOT ONLY FIELD-LEVEL. The prior configuration disabled request bodies, locals, cookies, and headers - but nothing scrubs error.message, and schema-validation and post-hoc-validation failures are a ROUTINE retried path whose error messages embed the model's output by construction. That output is child-directed generated content. RULES. (1) A beforeSend hook REDACTS MESSAGE AND EXCEPTION-VALUE TEXT for the validation and provider fault classes, replacing them with the fault class, the correlation identifier, and the schema name. The diagnostic value lives in the correlation identifier, which reaches the AiCall row and the logs. (2) The default is DENY: an error type not explicitly known to be content-free is redacted. (3) Free tier limits are acknowledged rather than assumed away - 5,000 errors per month, ONE seat, 30-day retention across all three containers. A crash-looping worker can exhaust the monthly quota, so a client-side rate limit on error reporting is required, and one seat is a weak notification channel to be revisited.
- (decision) RESIDUAL GATE FIXES. (1) SPEND-CEILING REFUSAL IS ITS OWN FAULT CLASS - neither a client fault nor an upstream fault. Without it the global daily ceiling degrades into an infinite retry loop or a nonsensical 'retake your photo' prompt. It is TERMINAL, never retried, surfaced as a service-unavailable state, and it fires an operator alert. (2) ACCOUNT TIER IS EFFECTIVE-DATED, exactly as the timezone now is: FR-30a requires a tier change to take effect immediately against the current period, so the tier in force for a period must be resolvable historically rather than read from a mutable column that rewrites the past. The effective-dating machinery was introduced for timezone and never swept for its siblings. (3) THE WIRE CONTRACT IS A NAMED CONVENTION: one error envelope shape carrying the fault class and the correlation identifier, identifiers as strings, timestamps as UTC ISO-8601 with the account's zone applied only at render, and no implicit field omission. The spine had no API contract convention at all, which is a first-order divergence point between the two units that exist on day one. (4) Two stale reconcile artifacts removed: the queue-substrate justification that still cited a debit no longer performed, and the extraction-ownership wording that described content living on the Source Test while the entity model has a separate Extraction entity.
