# Spine Pair Review — n-test-reviewer

Lens: rubric walker. Reviewed `DESIGN.md` (385 lines) + `EXPERIENCE.md` (300 lines) against `references/validate.md`, `references/design-md-spec.md`, `.memlog.md` (67 entries), and `prd.md` + `addendum.md`.

## Overall verdict

`DESIGN.md` is close to handoff-ready: the token layer is complete and dark-paired, the sections are canonical and in order, and the accent-split / paper-vs-control / flat-bordered rules are stated tightly enough to be enforced in code review. `EXPERIENCE.md` is not. It is excellent on the four PRD journeys and on every decision the coaching session interrogated directly, and materially incomplete on everything the session never reached: the FR-25 grade dispute, FR-24a parent-side Explanation review, FR-15 timer configuration, FR-33 deletion, and profile management have surfaces named in the IA (or not named at all) with no behaviour, no states, and no components behind them. Separately, the single most concrete accessibility decision in the memlog — the four-carrier grade-state encoding — was dropped in distillation and two of its four literal labels were silently changed. Close the three critical findings and the high band before architecture consumes this; the medium and low bands can be absorbed into an Update pass.

## 1. Flow coverage — thin

Checked: every UJ name in PRD §2.3 against the Key Flows section; then every FR in PRD §4 against IA / Component Patterns / State Patterns for a reachable path.

All four journeys are present, named verbatim, with a named protagonist, numbered steps, an explicit **Climax** beat, and a failure/edge path (UJ-1 interruption note, UJ-2 Explanation-failure/at-cap/dispute note, UJ-3 PIN-cooldown + idle-timeout note). UJ-4 carries an italic note but no failure path, matching the PRD, which also gives UJ-4 no edge case. That part is **strong**.

The verdict is thin because whole requirement clusters have no flow and, in most cases, no surface either.

### Findings

- **critical** FR-25 (grade dispute) is mis-cited as **FR-23** and has no parent-side home or action. `EXPERIENCE.md` § Component Patterns → Explanation panel calls it "the FR-23 grade-dispute flag"; FR-23 is *Answer reveal*, and the dispute flag is FR-25. Worse than the citation: the self-reported gap understates this. FR-25's testable consequences require that flagged Questions appear in Parent View **with the student's answer, the recorded grade, and the grading rationale**, and that **a parent can override the grade, which recomputes the Attempt score and the affected Topic's Mastery**. Neither spine contains a grade-override affordance anywhere, and the IA has no Parent View screen that could hold one. A score-and-Mastery-mutating action is entirely absent from the UX contract. *Fix:* correct the citation to FR-25 in the Explanation panel row; add a Parent View **Flagged answers** IA row (or fold it into the Topic drill-down / a per-Attempt results view in Parent View); add a Component Patterns row specifying the four required data elements plus the override control; add a State Pattern for what the student sees after an override lands (the score changed — this is the same "must not read as the app changing its mind" problem already solved for ungraded resolution, and the answer must be consistent).
- **critical** FR-15 (timer configuration) has no surface, no control, and no owner. The optional per-Practice-Test countdown timer is load-bearing in `DESIGN.md` (`timer-display`, `{typography.timer}`), in `EXPERIENCE.md` (Component Patterns, State Patterns timer expiry, Accessibility Floor hard case #2), and in both UJ-1 step 9 and UJ-2 step 2 — but nothing in the IA, Component Patterns, or any flow says where a parent turns it on or sets a duration. The Accessibility Floor asserts "the timer stays optional, parent-controlled, and default off" with no control to point at. *Fix:* name the surface that owns timer configuration (Draft review is the natural home — it is the last parent gate before release, and UJ-1 step 8 releases from there) and add a Component Patterns row: default off, per-Practice-Test, duration entry, and whether it is editable after release.
- **high** FR-24a's parent-side path has no surface. The bad-Explanation flag is specified inside the student results Explanation panel, and the Admin **Flagged Explanations** queue exists in the IA — but FR-24a's first testable consequence is that *a parent can read every Explanation shown to their student, and flag one as bad*. There is no Parent View screen where a parent reads Explanations, and no flag control on the parent side. This is the same class of gap as the grade dispute and was not self-reported. *Fix:* add the parent-side Explanation read/flag path — most cheaply as an expandable Explanation on the Parent View per-Attempt results / Topic drill-down rows, which already render Question content in Literata as paper role.
- **high** FR-33 (parent-initiated deletion) has no UX at all. The requirement carries hard, testable UX constraints: every deletion requires explicit confirmation **naming what will be destroyed** and stating it cannot be undone, and Student Profile / Parent Account deletion requires **the account password, not the Parent PIN**. `DESIGN.md` names `error` as the "destructive confirm" color, so the token anticipates a pattern that `EXPERIENCE.md` never specifies. *Fix:* add a State Patterns row for destructive confirmation (what is named, password re-auth, non-undoable statement) and a Component Patterns row for the confirm dialog; `dialog` already has a visual spec.
- **medium** Parent Account sign-up / sign-in / password reset (FR-1) are absent from the Information Architecture, which otherwise enumerates every screen including Admin sign-in. Both UJ-1 and UJ-3 open "already signed in", so no journey forces them. *Fix:* add the auth rows to the IA even if they carry no bespoke design, or state explicitly that auth is out of the spine's scope and inherited from the `n-electric` stack.
- **medium** FR-4 device-to-Student-Profile binding is unspecified. Student Mode is "the default state of the device" showing one profile, but nothing says how a device becomes bound to Noah, or what a parent does on a Family-tier account with five profiles and one tablet. *Fix:* one line in the IA or in the Students row naming where binding is set.
- **medium** Confirmed and refined — `Parent View → Students` and `Parent View → Settings` have no Key Flow. Both PRD §6 and FR-3 / FR-33 populate them, so the gap is not that a journey is missing but that the two screens are IA rows with **zero downstream content**: no component rows, no states, no empty states, no copy rules. FR-3 also specifies archiving as distinct from deletion, which appears nowhere. *Fix:* either give both screens minimal Component Pattern and State Pattern rows (archive vs delete, PIN change, allowance visibility, data deletion), or state deliberately that they inherit default MUI form treatment with no bespoke spec — but say which.

## 2. Token completeness — adequate

Extracted all 22 color tokens, 10 typography roles, 3 radii, the spacing scale, both density sets, both tap-target floors, and 12 component objects. Extracted every `{path.to.token}` reference in both files.

**Every cross-reference resolves.** All 6 `EXPERIENCE.md` references (`{colors.success}`, `{colors.error}`, `{colors.text-secondary}`, `{colors.warning}`, `{spacing.tap-target.student}`, `{spacing.tap-target.parent}`) resolve to `DESIGN.md` tokens by name, and no hex or px value is restated in `EXPERIENCE.md`. Every color has a light/dark pair. No token is referenced-but-undefined and no token is defined-but-unused.

### Findings

- **high** No focus-ring token and no hover-tint value, in a system that bans shadows. `DESIGN.md` § Elevation & Depth commits every interactive surface in the product to "a visible outline in the surface's `primary`" for focus and "a subtle background tint toward `background-default`" for hover — with no outline width, no offset, and no tint value or opacity. This is the one place downstream code cannot mirror the spine, and it applies to every control on every screen. *Fix:* add `colors.hover-tint` / `colors.hover-tint-dark` as hex (or state the tint as an explicit alpha over `background-paper`), and add `focus-ring: { width, offset, color: '{colors.primary}' }` to the frontmatter, with the AA non-text contrast check (3:1 against both adjacent surfaces) stated.
- **medium** Only one contrast pair is published. `DESIGN.md` § Colors states question-body-on-paper (16.56:1 light / 14.05:1 dark) and asserts "every pair above is verified in both modes" without numbers — yet the memlog records measured values from the rendered mocks for exactly the load-bearing pairs: 6.50:1 secondary, 6.53:1 error, 5.93:1 warning (the Weak Area marker), 5.96:1 student teal, 6.52:1 parent primary as text and as button ground, lowest 5.47:1 overall. That data exists and was dropped. *Fix:* add a contrast table to § Colors carrying the measured values for on-primary/primary, error/paper, warning/paper, text-secondary/paper, in both modes.
- **low** Two frontmatter shapes deviate from `design-md-spec.md`: `typography.timer.fontVariantNumeric` is outside the spec's permitted subset (`fontFamily`, `fontSize`, `fontWeight`, `lineHeight`, `letterSpacing`), and `typography.measure.questionMaxWidth` is not a typography object at all. `spacing.density` / `spacing.tap-target` nest below the spec's flat scale. All three read cleanly and a resolver flattens them, so this is a defect only against the letter of the spec. *Fix:* optional — either accept and note the deliberate extension, or move `measure` to a sibling `layout` key.
- **low** `components.dialog.scrim` / `scrimDark` are raw `rgba()` literals inside the components block rather than tokens in `colors`. Every other color in the system is a named token. *Fix:* promote to `colors.scrim` / `colors.scrim-dark` and reference them.

## 3. Component coverage — thin

Extracted every component name used anywhere in either file and cross-checked `DESIGN.md`.Components (visual) against `EXPERIENCE.md`.Component Patterns (behavioural).

Eight components have both halves and both halves are real rules: Practice Test card, Question container, Explanation panel, Answer-key row, Question map cell, Mastery row, Page thumbnail, Timer display. Naming is identical across all sections of both files. That part is strong.

### Findings

- **critical** The four-grade-state encoding was dropped, and two of its four literal labels were changed. The memlog resolves this concretely as the canonical pattern to carry into the spines: **three redundant non-colour carriers plus hue** — (a) icon frame shape and border style (solid circle / solid circle / dashed circle / dotted square), (b) glyph (check / cross / dash / ellipsis), (c) literal text label, (d) row left-rule texture (solid / 45° hatch / dashed / dotted), with correct and incorrect deliberately sharing a frame shape but differing on every other axis. Neither spine carries any of it. `DESIGN.md` § Components → Answer-key row names four colors and says "icon + text label + color"; `EXPERIENCE.md` § Grade States says "Icon + [label]" with no icon named anywhere in the product. **No icon set, glyph, or shape is specified in either file**, so "never colour alone" is an assertion a builder cannot implement, and the Accessibility Floor's hard case #4 rests on it. Additionally the decided labels were `'Correct' / 'Not correct' / 'Unanswered' / 'Not graded yet'` — the memlog states explicitly that the incorrect label is **"Not correct", not "Wrong"**, "consistent with the requirement that a wrong answer never read as punishment". `EXPERIENCE.md` § Grade States ships `'Correct' / 'Incorrect' / 'Not answered' / 'Not graded yet'`, contradicting the decision on two of four, and UJ-2 step 6 propagates "Not answered". *Fix:* restore the four-carrier encoding table into `DESIGN.md` § Components (it is visual spec) and restore the exact decided labels into `EXPERIENCE.md` § Grade States, `DESIGN.md` § Components → Answer-key row, and UJ-2 step 6. If the labels were changed deliberately, record that as a decision — right now it reads as distillation drift.
- **medium** Six components carry behaviour with no visual spec: **Score header** (the most emotionally loaded element in the product — no type role assigned; § Typography mentions score displays only inside the `tnum` rule), **Trend sparkline** (no stroke, fill, size, or color — and it is a chart in a system with no chart language), **Profile switcher** (persistent chrome, appears in every Parent View screen and in UJ-3), **Legibility result**, **Draft review list**, and the **cost block** the weighted-regenerate control is gated behind. *Fix:* add rows to `DESIGN.md` § Components for at minimum Score header, Trend sparkline, and Profile switcher; the other three can inherit paper/control roles if that is stated.
- **medium** Two components carry visual spec with no behaviour: `dialog` and `snackbar` have `DESIGN.md` rows but no `EXPERIENCE.md` Component Patterns entry. Snackbar in particular is undefined on duration, dismissal, stacking, and live-region announcement — and § Accessibility Floor requires that "every state change that matters (grade resolution, save, submit confirmation) [is] announced via a live region", which is presumably the snackbar's job. *Fix:* add behavioural rows for both, or drop `snackbar` from `DESIGN.md` if nothing uses it.
- **medium** The FR-28 activity summary ("unstarted vs completed") appears only as three words in the IA row for the Analytics dashboard. It is the v0 answer to "did my child do it" (PRD §9.2), it leads the dashboard per FR-28, and the rendered mock leads with it — but it has no Component Patterns row, no visual spec, and no appearance in UJ-3's steps. *Fix:* add a Component Patterns row and put it in UJ-3 step 2 or 3.
- **low** `answer-key-row` is the only paper-role component object with no `background` key, while `question-container` and `explanation-panel` both declare it. *Fix:* add `background: '{colors.background-paper}'` for consistency.

## 4. State coverage — thin

Walked all 15 IA surfaces and listed the states each should carry (empty, cold-load, focus, error, offline, permission-denied), then checked § State Patterns.

What is covered is covered exceptionally well — submit-with-gaps, timer expiry, interrupted Attempt, Explanation loading/failure/at-cap, degraded grading, late grade resolution, generation in flight and failure, durable drafts, silent PIN timeout with uncommitted-input persistence, four distinct empty states, PIN cooldown, thin Extraction. Each states the rejected alternative and the reason. Fifteen rows is a lot of real behaviour.

The gaps are systematic rather than random: they are the states nobody asked a question about.

### Findings

- **high** No camera-permission-denied state anywhere. § Foundation commits to "camera access through the browser" and the entire capture flow (UJ-1 steps 3–4, Capture strip, Legibility result) assumes the viewfinder opens. A browser camera permission denial or an unavailable camera is the single most likely hard failure in the parent's five-minute kitchen path, and camera-roll upload — the UX-originated addition in this very session — is the ready-made fallback. *Fix:* add a State Patterns row: permission denied or camera unavailable falls back to camera-roll selection with a plain statement, never a dead end.
- **high** No offline / network-loss state anywhere, in a product where PRD §9.2 states network is required and every grade, Explanation, and generation is a server call. The closest coverage is "Interrupted Attempt survives interruption", which addresses app-backgrounding, not connectivity. A tablet that drops wifi mid-Attempt is the realistic case. *Fix:* add a State Patterns row covering submit-while-offline (FR-18 attempt persistence is the mechanism), Explanation request while offline (it must be distinguishable from the FR-24 failure state and from the at-cap state, since the copy rules differ), and generation while offline.
- **medium** FR-32's expired-Page-Image state is absent. The FR is explicit: "Surfaces that would otherwise display a Page Image show an expired state rather than a broken image or an error." The capture strip and any Source Test review view are those surfaces. *Fix:* one State Patterns row.
- **medium** No cold-load / first-paint state for any surface. Student Home, the Analytics dashboard, the Mastery table, and Pending drafts all render server data; only the Explanation panel and Generation progress specify a loading treatment. Given the ban on motion outside four named cases, whether a skeleton is permitted is a real open question a builder will resolve by guessing. *Fix:* one rule — what the product shows while a list or dashboard loads, and whether it is exempt from the motion ban.
- **medium** Admin's three surfaces have no states at all. "Same tokens, no craft" is a defensible decided posture for polish, but the Flagged Explanations queue is named in UJ-4 as the one Admin screen with a claim on real attention, and an empty queue (the normal case) has no treatment. *Fix:* either state explicitly "Admin inherits default states and receives no designed empty states" — which is what the memlog decided — or give the flagged queue its empty and worked states.
- **medium** No error state for Upload / Classify. Legibility failure, thin Extraction, and generation failure are all covered; an upload that fails outright, a Page Image over a size limit, and an 11th page against the 1–10 ceiling (FR-5) are not. The FR-5 ceiling is mentioned in the Capture strip row but with no at-limit behaviour. *Fix:* one row covering the capture ceiling and upload failure.

## 6. Bloat & overspecification — strong

No pixel specs where a token covers it — `EXPERIENCE.md` contains no hex and no px, and every dimension in `DESIGN.md` is a token definition rather than a per-component override. No persona restatement, no FR restatement, no scope recap. The tables carry the load; prose is reserved for rules that need a reason. `DESIGN.md` § Brand & Style earns its editorial voice ("the score appears; it does not perform", "two rooms, one building") and stays inside `DESIGN.md`, where the rubric allows it. The two "Decisions That Travel Upstream" and "Open Questions" sections are exactly the kind of invented section that earns its place: they are what stops architecture inheriting a contradiction.

### Findings

- **medium** The responsive rule is stated twice, near-verbatim, in both files. `DESIGN.md` § Layout & Spacing paragraphs 5–6 and `EXPERIENCE.md` § Responsive & Platform both carry "Breakpoint-specific layouts only where the device changes the task", both name the same two screens, and both carry "Density is split by surface; breakpoint is independent". Duplication across a spine pair is a drift surface. *Fix:* keep the density-vs-breakpoint invariant in `DESIGN.md` (it is a spacing-token rule) and the per-screen layout table in `EXPERIENCE.md`, with a pointer rather than a restatement.
- **low, preference** Several § State Patterns cells carry rejected-option archaeology — "Blocking was rejected (it traps a student…); silent submission was rejected (it punishes a mis-tap)", "Auto-retry was rejected: it can silently double a wait". This is memlog content. It is defensible here as guard-rail against relitigation, and it is genuinely short, so this is a preference, not a defect. If trimmed, keep the *rule* and drop the *rejected* clause.
- **low, preference** § Open Questions runs 17 rows, of which 11 are post-launch revisit triggers rather than open questions. They are valuable and correctly labelled, but they read as one list doing two jobs. *Fix:* split into "Open" (1–5, 17) and "Revisit conditions" (6–16).

## 7. Inheritance discipline — adequate

`sources` frontmatter in both files resolves (`../../prds/prd-n-test-reviewer-2026-08-29/prd.md` and `addendum.md` both exist; `EXPERIENCE.md` additionally sources `./DESIGN.md`, correct). All four UJ names are verbatim from PRD §2.3. Glossary usage is exact throughout both spines — Practice Test, Source Test, Page Image, Attempt, Grade Level, Student Profile, Parent View, Student Mode, Account Tier, Upload/Generation Allowance, Weak Area, Mastery, Topic, Question Format and its three values, Extraction, Explanation, Analytics — with no coined synonyms and no drift. Component names are identical across all sections of both files. All token references resolve.

### Findings

- **high** The Mastery formula in § Grade States contradicts FR-26 by omission. The spine states "**Mastery = correct / (correct + incorrect) per Topic**" as the whole rule. FR-26 adds two constraints the spine never carries: Mastery is computed over a **rolling window of the 5 most recent qualifying Attempts** that included that Topic, and **only the first Attempt on a given Practice Test qualifies** — retakes are recorded and shown but never contribute. The rolling window appears in this spine only as a passing rationale for not drawing per-Topic trend lines. The retake exclusion appears nowhere at all, yet UJ-2 ends on "He taps **Retake**" and § Component Patterns offers Retake on the results screen with no indication that retaking moves nothing on his mother's dashboard. That is a user-visible consequence with no UX answer. *Fix:* state the full FR-26 rule in § Grade States, and add a line on whether the parent-facing Analytics or the student-facing Retake surfaces the fact that retake Attempts do not count. PRD SM-C3 exists precisely to catch this being misused, so it is not a detail.
- **high** FR-28's "Mastery is presented per Topic, **filterable by Subject**" is dropped. The Mastery table is specified as a flat ranked list sorted weakest first with no Subject filter, and PRD UJ-3 additionally describes "a list of his most-missed topics across subjects". With one Subject this is invisible; with Math and Science released it is a missing control. *Fix:* add the Subject filter to the Mastery table Component Patterns row, or record dropping it as a deliberate v0 decision with its rationale.
- **high** § Open Questions #1 records a question the memlog closed. The entry asks whether the smart fraction field needs an authored accessible-math representation and marks it "Open — falls out of the accessibility hard case, not answered". The memlog's final entry resolves it concretely: "typographic fractions are marked `role='img'` with a spoken text alternative (e.g. 'five sixths') so a rendered fraction is never announced as 'five six', **closing the Q18 hard case**" — and `key-take-test.html` applies the same treatment to the typed input as it live-renders. A resolved accessibility decision recorded as open will be re-decided, probably differently. *Fix:* move the `role="img"` + spoken-text-alternative rule into § Accessibility Floor hard case #1 and § Component Patterns → Smart fraction field, and delete Open Question #1.
- **medium** Confirmed, with a refinement — the tablet question-map rail lost its binding constraint. § Responsive & Platform allocates the tablet surplus to "a persistently visible question map beside the Question", but drops the memlog's explicit qualifier: the rail shows **answered/not-answered state only — no score, no correctness hint, nothing that would constitute mid-test feedback**. PRD §9.1 requires "no mid-test feedback", so this is the constraint that keeps a persistent rail legal. *Fix:* restore the qualifier to the § Responsive & Platform Take Test row.
- **medium** The Weak Area threshold is never stated in either spine. FR-27 sets it at **below 60% Mastery** with the five-question floor. `EXPERIENCE.md` names the five-question floor four times and the 60% threshold zero times; `DESIGN.md` gives `mastery-row` a `barFillOk` and a `barFillWeak` with nothing saying which fires when. The rendered mock even has an explicit threshold divider row. A builder cannot render the Mastery table without inventing a number. *Fix:* state the 60% threshold in § Component Patterns → Mastery table and in `DESIGN.md` § Components → Mastery row.
- **medium** Confirmed as stated — the Q13a generation-progress reading is an unconfirmed interpretation presented as settled. The memlog is explicit that the user answered "A" among three A-variants and that "generation continues server-side and no work is lost" is the reviewer's *interpretation*, to be corrected if wrong. § Open Questions #17 flags this honestly, but § State Patterns → "Generation in flight", § Voice and Tone constraint 3, and UJ-1 step 6 all state it as decided fact with no hedge, and the copy constraint is written as binding. The risk is asymmetric: if the interpretation is wrong, the shipped copy tells a parent something false. *Fix:* get the user's confirmation before handoff. It is a one-question ask, and until it lands, mark the State Patterns row provisional rather than only footnoting it 17 rows later.
- **medium** Confirmed as stated — the trend sparkline's window is unspecified. § Component Patterns says "across recent Practice Tests"; Open Question #3 acknowledges it. The rendered mock uses five attempts, which is at least a defensible default and is not carried into the spine. The gap is slightly wider than reported: the sparkline also has no visual spec at all (see §3), and no stated behaviour when fewer than the window's worth of Attempts exist — which is the Free-tier default case the empty-state work went to such lengths to handle. *Fix:* fix the window (five recent Practice Tests matches the mock and the FR-26 window), and say what renders below that count.
- **medium** Confirmed as stated — Open Question #4, the profile switcher's "outstanding work" signal, has a mitigation with no mechanism. § Information Architecture commits to it "where that is cheap" — an escape hatch that will be read at build time as "skip it", quietly removing the mitigation that made the one-child-at-a-time Analytics scope acceptable for Family tier. *Fix:* decide it. The FR-28 unstarted count is already computed for the dashboard, so "cheap" probably resolves to "yes".
- **low** FR-9a's thin-Extraction warning is reduced to "Warned before generation fires, with proceeding allowed". FR-9a requires the warning to carry **the usable-question count**, which is the whole basis on which the parent decides to proceed or retake. *Fix:* name the count in the State Patterns row.
